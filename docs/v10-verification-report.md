# V10 嵌入引擎全方位验证报告

> 测试日期：2026-07-12 ｜ 测试环境：WSL2 (Linux) + torch 2.12.0 CPU
> 对照对象：V9v3（已验证，见 `v9v3-verification-report.md`）
> 评测脚本：`tools/v9v3_verify.py` 同方法论移植（本仓库 `F:/v10_verify_tmp/v10_verify.py` 临时运行，未污染源码目录）

## 1. V10 是什么

`F:\代码\v10原始版` 是 **BaizeEmbeddingV10 — 纯源池架构（Pure Source Pool）**，PyTorch 实现。
它是 **V9 的蒸馏学生模型**（训练时用 V9 当 teacher 蒸馏），架构上砍掉了 V9v3 的 Linear+LayerNorm「伪 Transformer」层：

| 项 | V9v3 | V10 |
|---|---|---|
| 架构 | Embed → 6×Linear+LN+源池 → Proj → LN → L2 | Embed → 6×纯源池 → 瓶颈72d → Proj → LN → L2 |
| 参数量 | 3.15M | **1.93M** |
| 权重体积 | 12.3MB | **7.73MB** |
| 输出维度 | 1024（L2 归一） | 1024（L2 归一） |
| Tokenizer | `ord(c)%4096`，max_len=96 | `ord(c)%4096`，max_len=96 |
| 实现语言 | 纯 C（libc+libm） | PyTorch（需 C 移植才能上 MCU） |

源池三速（fast=0.85 / med=0.95 / slow=0.995），每速 24 维 → 池状态 72 维 → 投影到 1024。

## 2. 六维评测结果

### A. 引擎完整性 ✅
- 输出维度 = **1024**，L2 范数 ≡ **1.000000**
- 确定性：同输入两次输出 **bit 一致**
- 稳定性：200 条随机中文，**NaN/Inf = 0**
- `load_state_dict(strict=False)`：**缺失键=[]，多余键=[]**（权重与模型结构完全匹配）

### B. 语义判别（与 V9v3 同题三元组）
| 查询 | 相关 | 不相关 | V10 | V9v3 |
|---|---|---|---|---|
| 找上次聊装修的朋友 | 小王微信(0.818) | 健身(0.209) | ✅ | ✅ 0.740/0.248 |
| 苹果手机多少钱 | iPhone(0.282) | 香蕉(0.588) | ❌ | ❌ 0.141/0.377 |
| 明天上午的会议提醒 | 会议(0.561) | 红烧肉(0.438) | ✅ | ✅ 0.354/0.035 |
| 帮我记一下张三的电话 | 张三(0.525) | 天气(0.286) | ✅ | ✅ 0.313/0.169 |
| 减肥餐食谱 | 鸡胸肉(0.400) | 足球(0.460) | ❌ | ✅ 0.382/0.357 |

**V10 通过 3/5，V9v3 通过 4/5。**
- 两引擎**共同失败**于「苹果」多义（蒸馏自同一 teacher，多义缺陷被继承）。
- V10 的绝对余弦普遍更高（向量空间更「张开」），但「减肥餐」一例以 0.400<0.460 微弱落败，V9v3 以 0.382>0.357 险过——属校准差异，非结构劣势。

### C. Top-k 检索（与 V9v3 同语料）
语料 7 条多主题，3 个查询：
- Q「找上次聊装修的朋友」→ Top1=小王微信，Top3 命中 ✅
- Q「明天开会提醒」→ Top1=会议，Top3 命中 ✅
- Q「健身计划」→ Top1=健身，Top3 命中 ✅

**V10 hit@1=3/3，hit@3=3/3；V9v3 同 3/3。** 实际检索场景两引擎均完美。

### D. 推理速度 ⚡
- **V10（torch CPU）：2.817 ms/embed**
- 对照 V9v3（native C）：7.43 ms/embed
- V10 在 Python/torch 下反而**快约 2.6×**——纯源池架构算子更少、参数更小。若移植为 C，在弱 MCU 上优势会更大。

### E. 上下文长度 / 96 截断
- 输入 96 字 == 输入 200 字（向量完全一致）→ **静默截断于 96 字符**，与 V9v3 同约束
- 96 字内增改 → 向量有差异（正常）
- 索引层需做长文本切片（同 V9v3 结论）

### F. 边界 case ✅（全 8 项通过，含空串不崩）
| case | finite | L2 |
|---|---|---|
| 空串 | ✅ | 1.0000 |
| 空格 / 单字母 / 数字串 / 英文 / 中英混排 / 超长100字 / 乱码 | ✅ | 1.0000 |

**关键优势：V10 空串不崩**（返回合法向量）；而 V9v3 的 `v9v3_embed("")` 会 **segfault**（已修于 `app/jianmu/v9v3_api.c`）。V10 对脏输入鲁棒性更好。

## 4. 结论与对参赛的建议

**V10 在「部署友好度」上全面优于 V9v3：**
- 更小（1.93M / 7.7MB）≈ 手表/ESP32-S3 EYE 的 RAM 压力减半；
- 更快（torch CPU 已 2.8ms，C 移植后预期显著低于 V9v3）；
- 更鲁棒（空串/脏输入不崩，无 V9v3 的 segfault 坑）；
- 架构更简单（无 Linear/LN/位置编码），**C 移植工作量比 V9v3 更小**。

**两点必须正视：**
1. **语义质量是 V9 的天花板**：V10 是 V9 的蒸馏学生，多义（「苹果」）等缺陷被继承。换更好的 teacher 或扩充训练数据，比换架构更能提语义。
2. **当前是 PyTorch，不能直接上 openvela**：需要把 `BaizeEmbeddingV10` 移植成 C（参考 `app/jianmu/v9v3_*.c` 的接法）。纯源池算子（Embedding 查表 + 三速几何衰减池 + 2 个 Linear + LayerNorm）比 V9v3 的 Transformer 残差栈更容易手写 C，且权重仅 7.7MB。

**下一步建议（按性价比排序）：**
1. 把 V10 移植成 C（`app/jianmu/v10_*.c`），替换当前 V9v3 引用 —— 体积/速度/鲁棒性三赢；
2. 长文本切片 + 预建索引 + Top-3 展示（缓解多义误排，两引擎通用）；
3. 若语义要再上一个台阶，回到训练侧换 teacher / 补多义训练数据，而非在部署侧补救。

> 备注：本评测在 WSL2 + torch CPU 完成，未做 MCU 真机验证；V10 的 C 移植与交叉编译需在 WSL2 中 `repo sync` 后实测。
