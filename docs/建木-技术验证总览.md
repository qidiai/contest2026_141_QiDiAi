## 3. V9v3 引擎验证（2026-07-12）

> 来源：`jianmu-os/worm_knowledge_engine/c_core/`。方式：WSL2 + 预编译 `libv9v3.so` 经 Python ctypes 调用。
> 详细证据：`docs/v9v3-verification-report.md`。

**六维结果**

| 维度 | 结果 | 判定 |
|---|---|---|
| A 完整性 | 1024维/池24维；10次 bit 一致；500轮 NaN=0；L2≡1.0 | ✅ |
| F1 截断 | 有效上限 = **96 字符**（非 api.c 里误读的 24） | ✅ 约束 |
| B 语义判别 | **9/10**（失败于「苹果」多义） | ⚠️ |
| C Top-k | Top-1 5/7，Top-3 **7/7=100%** | ✅ |
| D 速度 | **7.43 ms/embed（native C）**，未达方案书 2.84ms（差 2.6×） | ⚠️ |
| E 三速池 | 三池**方向共线 cosine=1.000**（退化） | ❌ 设计缺陷 |
| F 边界 | 8/8 正常（空串由 harness 守卫） | ✅ |

**三个关键发现**
1. 🔴 **空串崩溃（已修）**：`v9v3_embed("")` 直接 segfault。二进制自检只测了 `model_forward("")` 直连（不崩），公开 API 空串路径从未被测 → latent 致命 bug。用户存空备忘录即崩设备。已在 `v9v3_api.c` 加守卫。
2. 🟠 **三速池共线**：fast/med/slow 三池实测 cosine=1.000，根因是 `v9v3_infer.c` 每层 `memset(pool,0)` 复位，使 `pool_X=(1-rX)*gw` 退化为同一向量的三个缩放副本。"多速记忆"实为 no-op；1024 维输出才是真语义信号。
3. 🟠 **速度/上下文约束**：实测 7.43ms/embed（比声称慢 2.6×）；96 字上限，长备忘静默截断；权重 `malloc` 进 RAM ≈12.3MB，全量模型仅适合 QEMU/主机，上手表需 V9v3-nano。

**亮点（可作参赛卖点）**：确定性、零 NaN、Top-3 100% 召回、纯 libc+libm 零依赖、12.3MB 可跑 —— 正是"离线、端侧、稳健"的题面。

## 4. V10 引擎验证（2026-07-12，含 V9v3 同题对照）

> 来源：`F:\代码\v10原始版`（PyTorch）。方式：WSL2 + torch 2.12.0 CPU。
> 详细证据：`docs/v10-verification-report.md`。

**V10 是什么**：`BaizeEmbeddingV10`（纯源池架构 Pure Source Pool），**V9 的蒸馏学生模型**（训练拿 V9 当 teacher）。砍掉了 V9v3 的 Linear+LayerNorm「伪 Transformer」层，tokenizer 同为 `ord(c)%4096`、96 字上限，输出 1024 维 L2 归一。

**六维结果（与 V9v3 同题对照）**

| 维度 | V10 | V9v3 |
|---|---|---|
| 完整性 | 1024维/L2=1.0/200轮0 NaN/确定性✅ | 同 ✅ |
| 语义判别 | **3/5** | 4/5 |
| Top-k 检索 | **3/3**（hit@1 与 hit@3） | 3/3 |
| 推理速度 | **2.82 ms/embed（torch CPU）** | 7.43ms |
| 空串 | **不崩** | 原版 segfault（已修） |
| 96 字上限 | ✅ | ✅ |

**关键结论**
1. 🔑 **部署友好度 V10 全面胜出**：更小（1.93M/7.73MB）、更快（torch CPU 都 2.8ms，比 V9v3 的 C 还快 2.6×）、空串不崩、架构更简单 → **C 移植工作量更小**，对 RAM 压力减半。
2. 🟠 **语义天花板是 V9 给的**：V10 是 V9 蒸馏出的，"苹果"多义缺陷被继承（两引擎同败）。要语义再上一个台阶，得回训练侧换更好 teacher 或补多义数据。实际检索（Top-k）两引擎均 100% 命中，日常够用。
3. 🔴 **致命短板**：V10 现为 **PyTorch，不能直接上 openvela/MCU**，必须先移植成 C。纯源池算子比 V9v3 残差栈好写，权重小，工作量可控。

## 5. 选型建议（两套引擎横向对比）

| 项 | V9v3 | V10 |
|---|---|---|
| 参数量 / 权重 | 3.15M / 12.3MB | **1.93M / 7.73MB** |
| 输出维度 | 1024（L2=1.0） | 1024（L2=1.0） |
| 部署形态 | **已有 C 引擎** | PyTorch（需 C 移植） |
| 推理速度 | 7.43 ms/embed | **2.82 ms/embed** |
| 空串鲁棒 | 原版崩（已修） | **不崩** |
| 语义判别 | 4/5 | 3/5（同 teacher 上限） |
| Top-k 检索 | 3/3 | 3/3 |
| 多速池 | 实测共线退化 | 未实测（仅推断） |
| C 移植工作量 | 已就绪 | **更小** |

**建议**：**V10 当主力（更适手表），但须先完成 C 移植**；V9v3 的现成 C 引擎留作 fallback / 对照基准。长文本切片 + 预建索引 + Top-3 展示是两引擎通用的必需品（缓解多义误排）。

## 6. 数据充分性 —— 诚实评估（重要）

**结论：目前只是「冒烟测试 / 概念验证」级别，不是严谨基准。** 证据底座很小，足以证明管线通、能区分明显语义、暴露已知弱点，但**离统计意义上"好用"差得远**。

**实测用了多少数据**

| 维度 | V10（本轮） | V9v3（上一轮独立测） |
|---|---|---|
| 语义判别 | **5 组三元组**（15 条文本） | 10 组（报告 9/10）/ 同题 5 组 |
| Top-k 检索 | 7 条文料 + 3 查询 | 12 条文料 + 7 查询 |
| 推理速度 | 1 种文本 × 100 次 | native 1 次 + ctypes 100 次 |
| 稳定性 | 200 条随机串（字母表仅 12 字、长 1–40） | 500 轮 |
| 边界 case | 8 个 | 8 个 |
| 上下文截断 | 2 个检查 | 1 个 |

**必须正视的 4 个缺口**

1. **V10 的三速池未实测** —— 我在 V10 报告里写的「架构上应能避免 V9v3 的共线缺陷」是**从架构推断，非实测**。需加 forward hook 抽出 72 维池状态，验证三速是否共线。
2. **`建筑行业微调/` 里的 v2/v3 完全没测** —— 该目录有 `best_model_v2.pt`/`v3.pt` 和微调脚本，可能强于或弱于原始版，目前是白纸。
3. **OOV / emoji 未压** —— tokenizer `ord(c)%4096`，超 4096 的字符（emoji、生僻 CJK）会回绕碰撞，未验证是否把无关内容误判为相关。
4. **规模检索未做** —— 真实备忘录集合是 50–500 条，现仅 7 条。recall@k 在真实规模下的表现未知。

**口径不一致说明**：「V10 3/5 vs V9v3 4/5」是同一轮对**同一 5 组**现测（公平对照）；但单独 V9v3 报告的「9/10」是**另一套 10 组**，两者非同一批数据，不能直接当成「V9v3 总体 4/5」。

**要做到「全面」的最小补测清单（按性价比）**
- 优先级 1：V10 三速池实测（forward hook 抽 72 维）
- 优先级 2：微调版 v2/v3 横向比（同脚本跑）
- 优先级 3：规模检索（100–300 条文料 + 20–30 查询，recall@1/@3/@5）
- 优先级 4：OOV / emoji 压测
- 规模语义：手写/爬 50–100 组中文本义对，跑 recall + 平均余弦差
