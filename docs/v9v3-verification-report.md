# V9v3 引擎全面验证报告

> 验证日期：2026-07-12 ｜ 验证者：吴八哥（Senior Developer）
> 引擎来源：`jianmu-os/worm_knowledge_engine/c_core/`（真实 V9v3 C 引擎）
> 权重：`v9v3_weights.baize`（12.3 MB，3,146,664 params）
> 验证方式：WSL2 + 预编译 `libv9v3.so` 经 Python ctypes 调用，六维评测脚本见 `tools/v9v3_verify.py`

---

## 0. 一句话结论

**V9v3 是一个"能用、语义基本到位、但有明确缺陷"的轻量嵌入引擎。** 它在本机实测 1024 维、输出严格 L2 归一化、500 轮无 NaN、确定性可复现，中文语义判别 9/10、Top-3 检索召回 100%。但存在 **1 个致命 bug（空串崩溃）**、**1 个设计缺陷（三速池共线退化）**、**速度未达方案书声称值**、**96 字符上下文上限** 四项必须正视的约束。下文逐条给出证据与建议。

## 2. 分项详述

### A. 引擎完整性 ✅
- `v9v3_init` 加载权重成功，输出维度 **1024**，语义池维度 **24**。
- **确定性**：同输入连续 10 次嵌入结果逐 bit 一致 → 无随机性，可复现、可缓存。
- **稳定性**：连续 500 次推理，NaN/Inf = 0。
- **L2 归一化**：多样本输出范数均 = 1.000 → 余弦相似度等价于点积，检索排序稳定。

### F1. 文本截断点（关键约束）✅
构造 `A×95+B`（96字）、`A×95+B+D`（97字）、`A×95+B+X×150`（300字）：
- 97字与96字嵌入**逐 bit 相同** → 超出 96 字符的内容被静默丢弃。
- 96字末位 B vs C 余弦=0.981（<1，确有差异）→ 第 96 位是有效边界。

> **结论：有效上下文上限 = 96 个 Unicode 字符（非 24）。** 一条备忘录超过 96 字会被截断，产品层需做分句/切片索引。

### B. 语义判别力 ⚠️ 9/10
10 组 (query, related, unrelated) 三元组，9 组满足 `sim(related) > sim(unrelated)`：

| query | related | unrelated | margin |
|-------|---------|-----------|--------|
| 找上次聊装修的朋友 | 0.740 | 0.248 | **+0.492** |
| 给妈妈买生日礼物 | 0.558 | 0.307 | +0.250 |
| 减肥餐食谱 | 0.490 | 0.076 | +0.413 |
| 明天的会议怎么准备 | 0.480 | 0.343 | +0.137 |
| 怎么煮咖啡 | 0.459 | 0.297 | +0.162 |
| 感冒了吃什么好 | 0.355 | 0.201 | +0.154 |
| 周末去哪玩 | 0.313 | 0.237 | +0.075 |
| 孩子作业辅导 | 0.315 | 0.280 | +0.034（临界） |
| 电池续航怎么样 | 0.428 | 0.414 | +0.014（临界） |
| ❌ 苹果手机价格 | 0.209 | 0.418 | **−0.209** |

**唯一失败是"苹果"多义性测试**：query"苹果手机价格"与"iPhone 15 多少钱"（0.209）竟低于"苹果派的食谱"（0.418）。
原因：tokenizer 是**字符级 + `codepoint % 4096`**，无分词/无词表学习，"苹果"二字在 query 与派食谱中共现，而 iPhone 文本不含"苹果"字 → 字符级模型把"水果义"误判为高相关。
**含义**：对高频多义字（苹果、银行、人民币…）判别力弱，是字符级架构的固有短板。

### C. Top-k 检索排序 ✅ Top-3 召回 100%
12 篇跨主题语料 + 7 条查询：

| query | Top-1 | 期望 | Top-3 含期望？ |
|-------|-------|------|----------------|
| 找上次聊装修的朋友 | 朋友 | 朋友 | ✅ |
| 明天的会议怎么准备 | 工作 | 工作 | ✅ |
| 想学做菜 | 育儿 | 美食 | ✅（美食在Top-3） |
| 周末去哪旅游 | 健身 | 旅行 | ✅（旅行在Top-3） |

**Top-1 命中 5/7（71%），Top-3 命中 7/7（100%）。** 对语义搜索产品而言，Top-3 召回完美，体验可接受；Top-1 偶有误排（如"想学做菜"首选育儿），可用 Top-3 展示 + 置信度阈值缓解。

### D. 推理速度 ⚠️
- **native C 直调：7.43 ms/embed**（100 次平均，WSL2 x86 主机）。
- ctypes 调用：7.16 ms/embed（含 Python↔C 开销，几乎无差异）。
- **与方案书声称的 2.84ms 差约 2.6×**：可能因评测机器/编译选项（`-O2` vs `-O3`）不同，或为最佳-case 估值。
- **对产品的含义**：目标可穿戴 MCU（远弱于 x86 主机）上会显著更慢，预计数十 ms 量级。若对 N 篇笔记做实时检索 = N×延迟，需靠 **V9v3-nano + 量化 + 预建索引** 解决（与方案书规划一致）。

### E. 多速语义池（fast/med/slow）❌ 揭示设计缺陷
`get_pools` 返回三套 24 维池，实测：
```
fast L2=0.681  med L2=0.227  slow L2=0.023
fast-med 余弦 = 1.000
fast-slow 余弦 = 1.000
med-slow  余弦 = 1.000
```
**三池方向完全共线（cosine=1.000），仅幅度不同。**

**根因（读 `v9v3_infer.c`）：** 每一层开头执行 `memset(pool_f/m/s, 0, …)` 重置，随后
`pool_X[i] = rX * pool_X[i] + (1-rX) * gw[i]`，其中 `gw` 是末位 token 经 write-gate 后的向量。
因每层先清零，`pool_X = (1-rX) * gw` —— 三个池是**同一个 gw 向量的不同标量缩放**，必然共线。
所谓"fast/med/slow 三速 EMA 记忆"实际退化为"单一向量的三个缩放副本"，**不提供额外判别信息**。

**含义**：1024 维输出（均值池化 + 投影）才是真正的语义信号；24 维池近乎冗余。不影响当前检索功能，但 SourcePool 的"多速记忆"卖点名不副实，后续若想用池做粗分类需重新设计（跨层/跨位置累积 EMA）。

### F. 边界 case ✅ / 空串崩溃 ❌（致命）
- 空格 / 英文 / 数字 / 单中文 / 乱码标点 / 超长300字 / 换行：**8/8 正常，无崩溃，L2=1.0**。
- **空串 `v9v3_embed("")` 直接 segfault**（已用隔离测试 `TEST3` 复现）。
  原因：二进制自检只测了 `model_forward("")` 直连（不崩），但**公开 API `v9v3_embed` 的空串路径从未被测试**，存在 latent 崩溃。
  **对产品的含义：用户存一条空备忘录就会让设备崩 → 必须在产品层（或引擎层）过滤空串。**

## 3. 风险清单（按严重度）

| 严重度 | 问题 | 影响 | 建议 |
|--------|------|------|------|
| 🔴 致命 | `v9v3_embed("")` segfault | 空备忘录致设备崩 | 产品层/引擎层加空串守卫（已在 `app/jianmu/v9v3.c` 修复） |
| 🟠 高 | 96 字符上下文上限 | 长备忘被截断丢信息 | 索引层做分句切片；UI 提示上限 |
| 🟠 高 | 速度 ~7.4ms（未达 2.84ms），目标 MCU 更慢 | 实时检索 N 篇会卡 | V9v3-nano + 量化 + 预建索引；检索走 Top-3 |
| 🟡 中 | 三速池共线退化 | "多速记忆"卖点落空 | 暂不影响检索；后续重设计池累积 |
| 🟡 中 | 多义字判别弱（苹果等） | 偶发误排 | Top-3 展示 + 置信阈值；未来换子词 tokenizer |
| 🟢 低 | RAM 12.3MB 整块 malloc | 手表/ESP32-S3 放不下全量 | 全量仅 QEMU/主机验证；上设备用 nano |

## 4. 对作品（建木）的含义与下一步

1. **核心管线已验证可用**：嵌入→索引→检索的语义质量真实成立（非占位哈希），这是参赛的底层底气。
2. **必须修的**：空串守卫（已修）、长文本切片索引策略。
3. **速度对策**：不要在主线程对全量笔记实时重算；改为"写入时增量索引 + 检索时只嵌 query + 点积扫描预存向量"。V9v3-nano 是上设备的前置条件。
4. **评测资产化**：`tools/v9v3_verify.py` 留作团队回归测试，每次换权重/换引擎都重跑，防退化。
5. **可作为亮点讲**：确定性、零 NaN、Top-3 100% 召回、纯 libc+libm 零依赖、12.3MB 可跑——这些正是"离线、端侧、稳健"的卖点。

## 5. 复现命令

```bash
# 在 WSL2 内，将 libv9v3.so 与 v9v3_weights.baize 置于同目录（规避中文路径）
python3 tools/v9v3_verify.py /path/to/libv9v3.so /path/to/v9v3_weights.baize
# 原生推理计时（对照 2.84ms 声称值）
./v9v3_infer /path/to/v9v3_weights.baize "性能测试文本"
```

> 注：本验证在 WSL2（x86 主机）完成，非目标硬件。目标可穿戴设备上的速度/内存表现需以真机或 QEMU 实测为准。
